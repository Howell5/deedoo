# Agent Note: Deedoo 官网与插件目录

Status: implemented

[English](2026-08-15-deedoo-website-plugin-directory.md) | 中文

## 问题

Deedoo 需要一个能够介绍并分发桌面应用的公开入口。DeepSeek Harness 插件也在多个独立 GitHub 仓库中快速出现，用户难以及时发现；同时，生态尚不足以支撑可靠的兼容性声明、自动风险评级或稳定的 Web 到桌面安装请求。如果先等待这些后续系统，产品和新生插件生态都无法尽快获得实用的公开入口。

## 决策

**产品首页和插件目录由同一个 TanStack Start 应用承载。** `/` 介绍 Deedoo 并链接到桌面构建，`/plugins` 和 `/plugins/:owner/:repo` 则在同一产品身份下提供发现与详情页面。Cloudflare Workers 渲染应用并提供静态资源，Wrangler 直接把应用部署到 Cloudflare。除非用户明确要求，否则 ChatGPT Sites 不作为回退。在两类体验规模都较小且紧密相关的阶段，共用部署无需维护第二个子域名、代码仓库和设计系统。

**初始目录以 GitHub 为主要信源，并通过评审整理。** [`apps/site/registry/plugins.json`](../../../../apps/site/registry/plugins.json) 记录公开代码仓库、编辑后的描述、分类和安装参数。定时工作流每六小时刷新 Star 数、Fork 数、主要语言、许可证和活动时间。默认排名使用 GitHub Star 数，访客还可按更新时间或收录时间排序。页面免责声明明确说明，收录不代表安全审查、兼容性保证或官方背书。

**注册表无需数据库即可向其他读取方开放。** `/api/plugins` 返回与服务端渲染所用内容相同的已校验记录。搜索和筛选在浏览器中针对有限目录运行，站点地图和 robots 响应则由 Worker 生成。新仓库通过代码评审收录，因此编辑字段和部署产物会一起变更。

**这个版本保留显式安装操作。** 当代码仓库具有已知安装参数时，详情页显示当前安装命令；否则引导访客查看 GitHub 安装说明。网站不会调用自定义 URL Scheme。后续一键安装必须先具备 Deedoo 协议处理器、用户明确同意、版本化请求载荷和客户端持有的校验，网页才能请求安装。

## 曾考虑的替代方案

**把插件目录放在独立的市场子域名和应用中。** 不采用：早期产品首页和目录共用导航、视觉身份、部署需求和一个小型运营团队。如果未来两者的发布周期或基础设施分离，路由边界仍保留拆分空间。

**使用托管数据库保存条目并开放公开提交。** 不采用：首批目录规模较小，公开 GitHub 元数据是主要变化输入，经过评审的 JSON 能让信源和编辑改动在 Git 中清晰可见。当账号、审核队列、发布者所有权或用户状态出现时，数据库才会产生明显价值。

**等到兼容性和风险评分完成后再上线。** 不采用：这些标签需要插件规范、可执行检查和足够的生态历史才能可信。带有明确免责声明的发现目录可以立即产生价值，也不会把未经验证的分数表述为事实。

**随网站一起实现桌面协议处理器。** 不采用：唤起本地应用并安装第三方代码会显著改变安全和授权要求。发现网站不依赖这项能力，并继续让用户显式控制安装。

## 后果

Deedoo 具备一个可部署的公开网站，其中包含产品定位、下载链接、首批 18 个项目、搜索、排序、详情页、公开 JSON 响应和爬虫元数据。目录运营只依赖 GitHub API 可用性和代码评审，不需要数据库或账号服务。按 Star 数排序简单清晰，但会偏向较早出现的仓库；被收录也不代表安全或运行时兼容。一键安装仍是独立的桌面能力，其协议、确认界面和失败处理可以单独设计，不会阻碍早期生态发现。
