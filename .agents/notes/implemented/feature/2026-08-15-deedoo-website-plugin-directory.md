# Agent Note: Deedoo website and plugin directory

Status: implemented

English | [中文](2026-08-15-deedoo-website-plugin-directory.zh.md)

## Problem

Deedoo needs one public destination that explains and distributes the desktop application. DeepSeek Harness plugins also appear across independent GitHub repositories faster than users can discover them, while the ecosystem is too early to support reliable compatibility claims, automated risk ratings, or a stable web-to-desktop installation request. Shipping those later systems first would leave both the product and its emerging plugin ecosystem without a useful public entry point.

## Decision

**The product home and plugin directory are one TanStack Start application.** `/` presents Deedoo and links to desktop builds, while `/plugins` and `/plugins/:owner/:repo` provide discovery and detail pages under the same identity. Cloudflare Workers renders the application and serves its static assets, and Wrangler deploys the application directly to Cloudflare. ChatGPT Sites is not a fallback unless the user explicitly requests it. The shared deployment avoids a second subdomain, repository, and design system while the two experiences remain small and closely related.

**The initial catalog is GitHub-first and review-curated.** [`apps/site/registry/plugins.json`](../../../../apps/site/registry/plugins.json) records public repositories, editorial descriptions, categories, and install specifications. A scheduled workflow refreshes stars, forks, language, license, and activity every six hours. The default ranking uses GitHub stars; visitors can also sort by update time or listing date. A listing disclaimer states that collection is not a security review, compatibility guarantee, or endorsement.

**The registry is open to other readers without adding a database.** `/api/plugins` returns the same validated records used for server rendering. Search and filtering run in the browser over the bounded catalog, and sitemap and robots responses are generated by the Worker. New repositories enter through code review, so editorial fields and the deployed output change together.

**Installation remains explicit in this version.** A detail page shows the current command when the repository has a known install specification and otherwise sends the visitor to its GitHub instructions. The website does not invoke a custom URL scheme. A later one-click flow requires a Deedoo protocol handler, explicit user consent, a versioned request payload, and client-owned validation before the web page can request installation.

## Alternatives considered

**Host the directory on a separate marketplace subdomain and application.** Rejected because the early product home and catalog share navigation, visual identity, deployment needs, and a small operating team. The route boundary preserves the option to split them if their release cycles or infrastructure diverge.

**Store listings in a hosted database with public submissions.** Rejected because the first catalog is small, public GitHub metadata is the main changing input, and reviewed JSON keeps provenance and editorial changes visible in Git. A database becomes useful when accounts, moderation queues, publisher ownership, or per-user state exist.

**Delay launch until compatibility and risk scoring exist.** Rejected because those labels need a package contract, executable checks, and enough ecosystem history to be credible. A clearly disclaimed discovery index creates immediate value without presenting unverified scores as facts.

**Implement the desktop protocol handler with the website.** Rejected because opening a local application and installing third-party code changes the security and consent requirements substantially. The discovery site does not depend on that capability and leaves installation under the user's explicit control.

## Consequences

Deedoo has one deployable public site with product positioning, download links, an 18-project initial catalog, search, sorting, detail pages, a public JSON response, and crawler metadata. Catalog operation is limited to GitHub API availability and code review, with no database or account service. Star ordering is simple and legible but favors older repositories, and repository presence says nothing about safety or runtime compatibility. One-click installation remains a separate desktop capability whose protocol, confirmation UI, and failure handling can be designed without blocking early ecosystem discovery.
